# RB-005: 5xx error spike after a deploy
Platform: any

## Symptoms
The rate of 5xx responses in the web server logs (IIS or Apache) is 3 times the 7-day baseline for 10 minutes or more. It usually affects every instance at once and starts within minutes of a deployment. Users see 500 Internal Server Error or 502 Bad Gateway pages.

## Diagnosis
Group the web server log by status to see which errors dominate. On IIS, sc-substatus narrows it: 500.19 means a broken web.config, 500.0 means an unhandled application exception, 502.x usually means a failing upstream or proxy. On Apache, read error.log next to the access log: AH00526 is a configuration syntax error, AH01114 (failed to make connection to backend) and AH01102 (error reading status line) mean a proxied backend is failing. Compare the time of the first error with the time of the last deploy. If every instance is affected, suspect the deploy; if only one instance is affected, use RB-003 (Windows) or RB-011 (Linux) instead. For exception details, check the Application event log on Windows (.NET Runtime 1026, ASP.NET warnings 1309) or the application's log and `journalctl` on Linux. Note the deployed version and the previous good version.

## Allowed actions
Diagnose only. The agent never fixes this automatically. It writes a diagnosis with the error breakdown, the deploy timing and the evidence, and proposes rollback_deploy to the previous good version. A rollback is Tier 2: it pauses for human approval with the approver ID and the plan hash.

## Rollback
If an approved rollback makes things worse, redeploy the version that was live before the rollback, which is a rollback of the rollback and also Tier 2. Verify after any deploy change that the 5xx rate is back to baseline for 10 minutes. If neither version is healthy, stop and page (Critical), because the cause may be outside the application (a database, a certificate or a dependency).
