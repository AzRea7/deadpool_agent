# RB-003: App pool crash or hang

## Symptoms
The site returns 503 Service Unavailable, or requests hang and time out. The load balancer health probe fails 3 times in 5 minutes on one instance while other instances stay healthy. A crash usually shows as a stopped app pool and 503s straight away. A hang usually shows as a running app pool whose requests pile up and never finish.

## Diagnosis
Check the app pool state on the instance: `Get-IISAppPool -Name <pool> | Select-Object Name, State` (or `appcmd list apppool <pool>`). Look in the System event log for WAS events: 5002 (pool disabled after a series of failures, called rapid-fail protection), 5009 (worker process terminated unexpectedly), 5010 (worker process failed to respond to a ping), 5011 (fatal communication error with the worker process). Look in the Application event log for event 1000 with w3wp.exe as the faulting application, and for .NET Runtime event 1026. In C:\Windows\System32\LogFiles\HTTPERR, the reason column tells crash from overload: AppOffline means the pool was disabled, Connection_Abandoned_By_AppPool means the worker process died mid-request, QueueFull means the pool is overloaded rather than crashed. For a hang, list long-running requests with `appcmd list requests /elapsed:30000`. If memory in w3wp has been climbing for hours, use RB-004 instead. If the failures started right after a deploy, also check RB-005.

## Allowed actions
Tier 1, automatic with limits: recycle_app_pool(name) on the affected instance only. If the pool is stopped, the action starts it. Limits: at most 1 recycle per instance per hour, canary on one instance first, and only pool names on the allowlist. Never recycle every instance at once. Verify after 2 minutes: the health probe passes 3 times in a row and the 503 rate is back to baseline. If the pool fails again within the hour, do not recycle again: escalate.

## Rollback
A recycle cannot be undone, but it changes no files or settings. Side effects: in-memory session state on that instance is lost, and the first requests after the recycle are slow while the app warms up. If the recycle does not recover the instance, or rapid-fail protection disables the pool again (event 5002), stop automatic actions for that instance and escalate with the evidence: pool state, the event log entries above, HTTPERR reasons and the time of the last deploy. A developer may need a crash dump, so note that capturing one (for example with ProcDump) is a manual step outside the action catalog.
