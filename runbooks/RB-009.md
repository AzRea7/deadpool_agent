# RB-009: Linux disk filling from Apache logs, the journal or package caches
Platform: linux

## Symptoms
The root filesystem (/) or the log volume is above 90% used, or growing fast enough to fill within 12 hours. Apache may stop writing logs or return 500 errors, and services that write to /var can fail with "No space left on device".

## Diagnosis
Check `df -h / /var/log` and the size of the usual suspects: `du -sh /var/log/apache2 /var/log/httpd /var/log/journal /var/cache/apt /var/cache/dnf /var/crash /tmp`. For Apache logs, look for rotated files that were never compressed or deleted (access.log.1 through access.log.60) and check that logrotate actually runs: `cat /var/lib/logrotate/status` shows the last rotation date, and `logrotate -d /etc/logrotate.d/apache2` shows errors such as "skipping because parent directory has insecure permissions". For the journal, `journalctl --disk-usage` compared with SystemMaxUse in /etc/systemd/journald.conf. If these folders explain most of the growth, this runbook applies. If `df` reports far more used space than `du` can find, or the big consumer is somewhere else, use RB-010.

## Allowed actions
Tier 0, automatic: delete_apache_logs_older_than(days=7) under the Apache log directory, journal_vacuum(max_mb=500), clean_package_cache, clear_tmp_older_than(days=7). Always dry-run first and check the file list and hash. Never delete outside these paths, and never delete the current access.log or error.log that Apache has open (that frees nothing; see RB-010).

## Rollback
Deleted logs cannot be restored unless archived. If logs must be kept, archive to Blob Storage before deleting. Confirm free space recovered after the action; if not, escalate. If logrotate was broken, propose the configuration fix (Tier 2) so the disk does not fill again.
