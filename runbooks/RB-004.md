# RB-004: Memory leak in an IIS worker process
Platform: windows

## Symptoms
The memory used by one w3wp.exe process climbs steadily for 2 hours or more above its normal baseline and does not drop after traffic falls. Available memory on the instance gets low, responses slow down, and the server may start paging. Eventually the app throws OutOfMemoryException, or the System log shows event 2004 (Resource-Exhaustion-Detector: low on virtual memory).

## Diagnosis
Match the worker process to its app pool with `appcmd list wp` (shows the process ID and pool name). Watch the Process(w3wp*)\Private Bytes and Memory\Available MBytes counters, or the same metrics in Log Analytics, and compare the slope with the 7-day baseline for that pool. A steady climb that survives quiet traffic points to a leak; a climb that follows traffic and falls back is normal load. Check whether the pool already has a private memory recycling limit configured. If the pool is crashing or returning 503s rather than slowly growing, use RB-003. If the growth started right after a deploy, also check RB-005.

## Allowed actions
Tier 1, automatic with limits: recycle_app_pool(name) on the affected instance only, at most once per instance per hour, canary first. After the recycle, open a ticket for the developers with the pool name, the memory slope, the deploy version and the time of the recycle, because a recycle treats the symptom, not the cause. Suggest a permanent fix as a proposal only: a private memory recycling limit for the pool, or a scheduled recycle, both Tier 2.

## Rollback
A recycle changes no files or settings. Side effects: in-memory session state on that instance is lost and the first requests are slow while the app warms up. Verify after 5 minutes that private bytes dropped back near baseline and the health probe passes. If memory climbs back within the hour, do not recycle again: escalate with the memory graph and the ticket.
