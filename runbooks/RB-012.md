# RB-012: Linux memory leak or OOM killer
Platform: linux

## Symptoms
Available memory on one instance falls steadily for 2 hours or more and does not recover when traffic drops. Apache children (or the application behind them) grow in resident memory, the instance starts swapping and slows down, and eventually the kernel OOM killer ends processes. The site then fails like RB-011, but the cause is memory.

## Diagnosis
Look in the kernel log for the OOM killer: `journalctl -k --since "-6h" | grep -i "out of memory"` shows lines such as "Out of memory: Killed process 4242 (apache2)" with the process size. Check MemAvailable in /proc/meminfo (or `free -m`) against the 7-day baseline, and the largest processes by resident memory with `ps -eo pid,rss,comm --sort=-rss | head`. A steady climb that survives quiet traffic points to a leak; a climb that follows traffic and falls back is load. Check whether Apache's MaxConnectionsPerChild is 0 (children never recycled), which lets a slow leak in a module or the application grow without limit. If Apache is down for a reason other than memory, use RB-011.

## Allowed actions
Tier 1, automatic with limits: graceful_reload_service(apache2) on the affected instance only, at most once per instance per hour, canary first. A graceful reload replaces the children and returns their memory. After the reload, open a ticket for the developers with the memory slope, the OOM killer lines and the deploy version, because a reload treats the symptom. Suggest a permanent fix as a proposal only: a non-zero MaxConnectionsPerChild, or a memory limit on the service unit, both Tier 2.

## Rollback
A graceful reload changes no files or settings and lets in-flight requests finish. Verify after 5 minutes that available memory is back near baseline and the health probe passes. If memory falls again within the hour, or the OOM killer fires again, do not reload again: escalate with the memory graph, the kernel log lines and the ticket.
